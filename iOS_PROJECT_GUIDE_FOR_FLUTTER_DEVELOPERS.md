## 2. The Xcode Project Layout

Unlike Flutter where everything lives in `lib/`, iOS projects have multiple **targets** (essentially separate compiled binaries sharing source code).

```
element-x-ios/
│
├── Package.swift              ← Swift Package Manager manifest (like pubspec.yaml)
├── project.yml                ← XcodeGen spec — the "source of truth" for the Xcode project
├── ElementX.xcodeproj/        ← Generated by XcodeGen (do NOT edit manually)
│
├── ElementX/                  ← Main app target
│   ├── Sources/               ← All Swift source code
│   └── Resources/             ← Images, fonts, localization, entitlements
│
├── NSE/                       ← Notification Service Extension (processes push notifications)
├── ShareExtension/            ← iOS Share Sheet extension
├── UnitTests/                 ← XCTest unit tests
├── UITests/                   ← XCUITest UI/integration tests
├── PreviewTests/              ← SwiftUI preview snapshot tests
├── AccessibilityTests/        ← Automated a11y tests
├── IntegrationTests/          ← Full integration tests against a real server
│
├── compound-ios/              ← Design system (like your own Flutter design package)
├── Tools/                     ← Scripts, Sourcery (codegen), SwiftGen
└── Secrets/                   ← API keys (Secrets.swift, gitignored)
```

> 💡 **Flutter parallel:** `ElementX/Sources/` = `lib/`. `project.yml` = `pubspec.yaml`. Multiple test targets = Flutter's `test/`, `integration_test/` split.

### How the project file is generated

This project uses **XcodeGen** — you never edit `ElementX.xcodeproj` directly. Instead you edit `project.yml` (or target-specific `target.yml` files), then run:

```bash
swift run tools setup-project   # first time
xcodegen generate               # subsequent changes
```

## 3. Swift Language Crash Course for Dart Developers

### Variables

```swift
// Dart
var name = "Alice";
final age = 30;

// Swift
var name = "Alice"      // mutable
let age = 30            // immutable (like Dart's final)
```

### Types & Optionals

Swift has **Optionals** (`T?`) — explicit nullability, like Dart's `T?` with null-safety:

```swift
var text: String? = nil    // Optional String
text?.count                // safe call (like Dart's ?.)
text!.count                // force unwrap — crashes if nil (like Dart's !)
text ?? "default"          // null coalescing (same as Dart's ??)

if let t = text {          // unwrap into new scope (Dart has no direct equivalent)
    print(t)               // t is non-optional here
}

guard let t = text else {  // early return if nil (very common Swift pattern)
    return
}
// t is non-optional here for the rest of the function
```

### Structs vs Classes

In Swift, **structs are value types** (copied on assignment) and **classes are reference types** (like Dart objects). SwiftUI `ViewState` and models are almost always `struct`.

```swift
struct HomeScreenViewState {
    var rooms: [HomeScreenRoom] = []
    var isLoading = false
}
// Assigning copies the struct — no shared state surprises
```

### Enums with Associated Values

This is Swift's killer feature — like Dart sealed classes (or `freezed` unions):

```swift
enum HomeScreenViewAction {
    case selectRoom(roomIdentifier: String)   // payload attached
    case markRoomAsRead(roomIdentifier: String)
    case leaveRoom(roomIdentifier: String)
    case logout
}

// Switch is exhaustive (compiler error if you miss a case)
switch viewAction {
case .selectRoom(let id):
    openRoom(id)
case .logout:
    logout()
// ...
}
```

### Protocols

Protocols are like Dart's abstract interfaces:

```swift
protocol ClientProxyProtocol: AnyObject {
    func joinRoom(_ roomID: String, via: [String]) async -> Result<Void, ClientProxyError>
    var roomSummaryProvider: RoomSummaryProviderProtocol? { get }
}

class ClientProxy: ClientProxyProtocol { ... }
class MockClientProxy: ClientProxyProtocol { ... }   // for tests
```

### Extensions

Add methods to any type anywhere:

```swift
extension String {
    var isValidEmail: Bool { contains("@") }
}
"user@example.com".isValidEmail  // true
```

### Property Wrappers

These are like decorators that add behavior to properties — heavily used in SwiftUI:

```swift
@Published var rooms: [Room] = []     // fires Combine event when changed
@State var isPresented = false        // local view state
@StateObject var viewModel = VM()     // owned observable object
@ObservedObject var viewModel: VM     // non-owned observable object
@EnvironmentObject var settings: AppSettings  // injected from parent
```

## 5. State Management: MVVM vs BLoC/Provider

This project uses **MVVM (Model-View-ViewModel)** with a base class called `StateStoreViewModel`.

### Flutter BLoC → Swift MVVM mapping

| Flutter BLoC | Swift MVVM (this project) |
|---|---|
| `Bloc<Event, State>` | `StateStoreViewModel<State, Action>` |
| `BlocEvent` (sealed class) | `ViewAction` (Swift enum with associated values) |
| `BlocState` | `ViewState` (Swift struct) |
| `add(event)` | `context.send(viewAction: .someAction)` |
| `BlocBuilder` | `@ObservedObject var context: ViewModel.Context` |
| `state.someField` | `context.viewState.someField` |
| `emit(newState)` | `state.someField = newValue` (mutates struct, fires `@Published`) |

### The ViewModel base class

```swift
// Base class (simplified)
class StateStoreViewModel<State, Action>: ObservableObject {
    @Published private(set) var state: State       // SwiftUI binds to this
    
    init(initialViewState: State) { state = initialViewState }
    
    // Override this to handle actions from the View
    func process(viewAction: Action) { }
    
    // Use this in subclass to mutate state
    // (e.g.) state.rooms = newRooms
}
```

### A real ViewModel example (HomeScreen)

```swift
class HomeScreenViewModel: StateStoreViewModel<HomeScreenViewState, HomeScreenViewAction> {

    // Dependencies injected at init — no service locator
    init(userSession: UserSessionProtocol, appSettings: AppSettings, ...) {
        super.init(initialViewState: HomeScreenViewState())
        
        // Subscribe to room list updates
        userSession.clientProxy.roomSummaryProvider?.roomListPublisher
            .receive(on: DispatchQueue.main)
            .sink { [weak self] rooms in
                self?.state.rooms = rooms.compactMap { HomeScreenRoom($0) }
            }
            .store(in: &cancellables)
    }

    override func process(viewAction: HomeScreenViewAction) {
        switch viewAction {
        case .selectRoom(let id):
            actionsSubject.send(.presentRoom(roomIdentifier: id))  // tell coordinator
        case .markRoomAsRead(let id):
            Task { await markRoomAsRead(id) }                      // async API call
        }
    }
}
```

### The View binds to the ViewModel

```swift
struct HomeScreen: View {
    @ObservedObject var context: HomeScreenViewModel.Context  // the ViewModel's context

    var body: some View {
        List(context.viewState.rooms) { room in
            RoomCell(room: room)
                .onTapGesture {
                    context.send(viewAction: .selectRoom(roomIdentifier: room.id))
                }
        }
    }
}
```

> 💡 **Key insight:** The View **never** holds logic or calls services. It only reads from `context.viewState` and sends `viewAction`s via `context.send(viewAction:)`. This is identical to the BLoC pattern constraint.

## 6. Combine Framework: Dart Streams → Swift Combine

Combine is Apple's reactive framework — equivalent to Dart's `Stream` + `StreamController` ecosystem (or RxDart).

### Core types

| Dart | Combine |
|---|---|
| `StreamController<T>` | `PassthroughSubject<T, Never>` |
| `BehaviorSubject<T>` (rxdart) | `CurrentValueSubject<T, Never>` |
| `Stream<T>` | `AnyPublisher<T, Never>` |
| `stream.listen(onData)` | `publisher.sink { value in ... }` |
| `stream.map(f)` | `publisher.map(f)` |
| `stream.where(f)` | `publisher.filter(f)` |
| `StreamSubscription` | `AnyCancellable` |
| `subscription.cancel()` | `cancellable.cancel()` (or dealloc) |
| `combineLatest` | `Publishers.CombineLatest(p1, p2)` |
| `StreamController.add(value)` | `subject.send(value)` |

### Subscriptions must be stored

In Flutter, you call `subscription.cancel()` in `dispose()`. In Swift, you store cancellables in a `Set<AnyCancellable>` — they auto-cancel when the set is deallocated:

```swift
// Flutter
late final StreamSubscription _sub;
void initState() { _sub = stream.listen(onData); }
void dispose() { _sub.cancel(); }

// Swift
var cancellables = Set<AnyCancellable>()

somePublisher
    .sink { [weak self] value in
        self?.handleValue(value)
    }
    .store(in: &cancellables)  // cancellable stored here; auto-cancelled when VM deallocated
```

### `@Published` is a Combine publisher

When a ViewModel's `@Published` property changes, SwiftUI automatically re-renders any view that reads it. No `setState()` needed.

```swift
@Published var state: HomeScreenViewState = .init()
// Changing state.rooms = [...] triggers SwiftUI re-render automatically
```

## 7. Async/Await: Nearly Identical, Small Differences

Swift's `async/await` is very similar to Dart's. The main differences:

```swift
// Dart
Future<String> fetchName() async {
  try {
    final result = await someAsyncCall();
    return result.name;
  } catch (e) {
    throw MyError(e);
  }
}

// Swift
func fetchName() async throws -> String {
    let result = try await someAsyncCall()   // try comes BEFORE await
    return result.name
    // Swift throws automatically propagate — no catch needed unless you want to handle here
}
```

### `Result<T, E>` type

This project uses `Result<T, Error>` extensively instead of throwing — like Dart's `Either` from `dartz`:

```swift
func joinRoom(_ id: String) async -> Result<Void, ClientProxyError> {
    do {
        try await client.joinRoom(id)
        return .success(())
    } catch {
        return .failure(.sdkError(error))
    }
}

// Caller:
switch await clientProxy.joinRoom(roomID) {
case .success:
    print("Joined!")
case .failure(let error):
    MXLog.error("Failed: \(error)")
}
```

### `Task` is like `Future()` in Dart (fire and forget from sync context)

```swift
// Dart
Future(() => doSomethingAsync());   // fire and forget

// Swift
Task { await doSomethingAsync() }   // fire and forget async work
Task { [weak self] in               // weak self to avoid retain cycles
    await self?.doSomethingAsync()
}
```

### `@MainActor` = `runOnMainThread`

```swift
@MainActor
func updateUI() {
    state.isLoading = false   // guaranteed to run on main thread
}

// Or using .receive(on: DispatchQueue.main) in Combine pipelines
```

## 8. Navigation: Coordinators vs Navigator 2.0

Flutter uses `Navigator` / `GoRouter`. This project uses a hand-rolled **Coordinator pattern**.

### The hierarchy

```
AppCoordinator                            ← App root
  └── UserSessionFlowCoordinator          ← Post-login tab bar
        ├── ChatsTabFlowCoordinator       ← Chats tab
        │     └── HomeScreenCoordinator   ← Home screen + pushes rooms
        │           └── RoomFlowCoordinator
        │                 └── RoomScreenCoordinator
        └── SettingsFlowCoordinator
```

### How navigation works

1. **ViewModel** sends an action to its `actionsSubject` publisher:
   ```swift
   actionsSubject.send(.presentRoom(roomIdentifier: id))
   ```

2. **Coordinator** subscribes to `viewModel.actionsPublisher` and handles navigation:
   ```swift
   viewModel.actionsPublisher.sink { action in
       switch action {
       case .presentRoom(let id):
           startRoomFlow(roomID: id)    // push a new screen
       }
   }
   ```

3. **NavigationStackCoordinator** wraps a SwiftUI `NavigationStack` and exposes:
   ```swift
   navigationStackCoordinator.push(coordinator)    // like Navigator.push
   navigationStackCoordinator.pop()                // like Navigator.pop
   navigationStackCoordinator.setSheetCoordinator(...)  // modal sheet
   ```

> 💡 **Flutter parallel:** A `FlowCoordinator` is like a `GoRouter` sub-route branch. Coordinators own navigation, ViewModels don't know about navigation — exactly like BLoC + GoRouter separation.

## 9. Dependency Injection: No BuildContext, Just Init Params

Flutter uses `BuildContext` + `Provider`/`Riverpod` to look up services. In this project, **all dependencies are injected through initializer parameters**. There is no service locator.

```swift
// Flutter (Provider)
final clientProxy = context.read<ClientProxyProtocol>();

// Swift (constructor injection)
class HomeScreenViewModel: StateStoreViewModel<...> {
    init(
        userSession: UserSessionProtocol,           // injected
        appSettings: AppSettings,                    // injected
        analyticsService: AnalyticsServiceProtocol  // injected
    ) { ... }
}
```

Coordinators create ViewModels and inject dependencies:

```swift
// HomeScreenCoordinator.swift
func start() {
    let viewModel = HomeScreenViewModel(
        userSession: userSession,
        appSettings: ServiceLocator.shared.settings,  // AppSettings is a rare exception
        ...
    )
    let view = HomeScreen(context: viewModel.context)
    navigationStackCoordinator.setRootCoordinator(self)
}
```

For **testing**, you pass mock implementations of the protocols:

```swift
let viewModel = HomeScreenViewModel(
    userSession: MockUserSession(),
    appSettings: AppSettings(),
    ...
)
```

## 11. The Matrix Rust SDK — The Real Backend

This is the most important thing to understand. **There is no `http` package, no `dio`, no Retrofit.** All Matrix API communication is handled by a Rust library compiled into an iOS framework.

### What it is

The [Matrix Rust SDK](https://github.com/matrix-org/matrix-rust-sdk) is a Rust library exposed to Swift via an auto-generated FFI (Foreign Function Interface) binding. The Swift package is at [matrix-rust-components-swift](https://github.com/matrix-org/matrix-rust-components-swift).

```swift
import MatrixRustSDK   // This is the entire SDK
```

### What the SDK handles (so you don't have to)

- All Matrix HTTP API calls (login, sync, send message, join room, etc.)
- Local SQLite database (caches rooms, messages, session data)
- Sliding Sync (the efficient incremental sync protocol)
- End-to-End Encryption (Olm/Megolm session management)
- Key backup and recovery
- Token refresh and OIDC

### Swift wrapper pattern

The SDK's raw Rust types are wrapped in Swift **Proxy** classes to add Swift-friendly error handling, logging, and Combine integration:

| Rust SDK type | Swift wrapper | File |
|---|---|---|
| `ClientProtocol` | `ClientProxy` | `Services/Client/ClientProxy.swift` |
| `Timeline` | `TimelineProxy` | `Services/Timeline/TimelineProxy.swift` |
| `RoomListProtocol` | `RoomSummaryProvider` | `Services/Room/RoomSummary/RoomSummaryProvider.swift` |
| `Encryption` | `SecureBackupController` | `Services/SecureBackup/SecureBackupController.swift` |

### SDKListener — Rust callbacks → Swift

Rust uses a callback/listener pattern for ongoing updates. `SDKListener<T>` bridges these into Swift:

```swift
// Register a listener that fires whenever the room list changes
roomListUpdateTaskHandle = roomList.entriesWithDynamicAdapters(
    listener: SDKListener { [weak self] diffs in
        Task { await self?.updateRoomsWithDiffs(diffs) }
    }
)
```

The returned `TaskHandle` **must be stored** in a property. If it gets deallocated, the listener stops firing. That's why you see `// periphery:ignore - retaining purpose` comments.

## 12. How Network Calls Work (No http.dart Here)

### Flutter pattern you're used to

```dart
final response = await http.post(
  Uri.parse('https://matrix.org/_matrix/client/v3/rooms/$roomId/send/...'),
  headers: {'Authorization': 'Bearer $token'},
  body: jsonEncode({'msgtype': 'm.text', 'body': 'Hello'}),
);
```

### This project's pattern

```swift
// In JoinedRoomProxy.swift
func sendMessage(_ message: String) async -> Result<Void, RoomProxyError> {
    do {
        try await timeline.send(content: .roomMessage(messageType: .text(.init(body: message))))
        return .success(())
    } catch {
        return .failure(.sdkError(error))
    }
}
```

`timeline.send(...)` is a call to the Rust SDK, which makes the actual HTTP request. From Swift's perspective, it's just an `async` call that either succeeds or throws.

### Call chain example: sending a message

```
User taps Send button
  → RoomScreen View sends ViewAction .sendMessage(text)
    → RoomScreenViewModel.process(.sendMessage(text))
      → JoinedRoomProxy.sendMessage(text)        ← Swift proxy
        → timeline.send(...)                     ← Rust SDK object
          → HTTP POST /_matrix/client/v3/rooms/{id}/send  ← actual network
```

### Error handling convention

All proxy methods return `Result<T, E>` — never throw to callers:

```swift
switch await roomProxy.sendMessage(text) {
case .success:
    state.composerMode = .default
case .failure(let error):
    MXLog.error("Send failed: \(error)")
    state.showErrorAlert = true
}
```

`MXLog` is the internal logging system wrapping Apple's `os.log`.

## 13. The Sync Loop — How Messages Stay Live

This project uses **Sliding Sync** — NOT polling. There is a persistent, long-lived connection to the homeserver.

### What is Sliding Sync?

Classic Matrix sync = HTTP long-poll (`GET /sync?timeout=30000`) — client waits, server responds when there are events, client immediately reconnects. Works but inefficient.

Sliding Sync = same idea but the SDK only syncs rooms in your current "viewport" (visible rooms), significantly reducing bandwidth. The SDK handles all of this automatically.

### The sync lifecycle

```swift
// AppCoordinator triggers this after login
clientProxy.startSync()
    → syncService.start()    // Rust SyncService starts the loop
```

The `SyncService` runs indefinitely:
1. Sends a sync request (with current room viewport)
2. Server holds it until events arrive (or 30s timeout)
3. SDK processes response, updates SQLite cache
4. SDK fires listener callbacks for changes
5. Back to step 1

### Network awareness

```swift
// In ClientProxy.init
networkMonitor.reachabilityPublisher
    .sink { reachability in
        if reachability == .reachable {
            self.startSync()    // restart when network comes back
        }
    }
```

When the phone goes offline, sync stops. When it comes back, sync restarts automatically.

### How updates reach the UI (push chain)

```
Server sends new message
  → SyncService (Rust) receives it
    → RoomListService fires RoomListEntriesUpdate diff
      → RoomSummaryProvider.updateRoomsWithDiffs()
        → roomListSubject.send(updatedRooms)   ← Combine
          → HomeScreenViewModel subscriber fires
            → state.rooms = newRooms           ← @Published
              → SwiftUI re-renders HomeScreen  ← automatic
```

This is **entirely push-based**. The UI layer never polls for data.

## 14. Room List and Timeline Data Flow

### Room List (`RoomSummaryProvider`)

**File:** `ElementX/Sources/Services/Room/RoomSummary/RoomSummaryProvider.swift`

There are three providers:

| Provider | Purpose |
|---|---|
| `roomSummaryProvider` | Main filtered list for the home screen |
| `alternateRoomSummaryProvider` | Full unfiltered snapshot (for last-message search) |
| `staticRoomSummaryProvider` | Non-observable list (for forwarding, share sheets) |

Filtering passes down to the Rust SDK — the SDK re-computes the room list and sends back diffs:

```swift
func setFilter(_ filter: RoomSummaryProviderFilter) {
    listController.setFilter(kind: .all(filters: [.normalizedMatchRoomName(pattern: query)]))
}
```

### Timeline (Per-Room Messages)

**File:** `ElementX/Sources/Services/Timeline/TimelineProxy.swift`

When you open a room, a `TimelineProxy` is created and calls `subscribeForUpdates()`. The SDK sends **diffs** (not full arrays) whenever messages change:

```swift
roomTimelineObservationToken = await timeline.addListener(
    listener: SDKListener { [weak self] timelineDiffs in
        self?.updateItemsWithDiffs(timelineDiffs)
    }
)
```

### Back-pagination (loading older messages)

When the user scrolls to the top of the chat:

```swift
// RoomScreenViewModel calls:
await timelineProxy.paginateBackwards(requestSize: 50)
    → timeline.paginateBackwards(opts:)   // Rust SDK
        → GET /_matrix/client/v3/rooms/{id}/messages  // HTTP request for older events
```

Old events come back through the same diff listener.

## 15. Authentication and Session Restoration

### New Login flow

**File:** `ElementX/Sources/Services/Authentication/AuthenticationService.swift`

```
User enters homeserver URL
  → AuthenticationService.configure(for: serverURL)
    → ClientBuilder.baseBuilder(...).build()   // Rust hits /.well-known
    → Returns available login modes (OIDC, password)

User chooses OIDC (recommended):
  → AuthenticationService.urlForOIDCLogin()    // Rust builds OIDC URL
  → App opens Safari / ASWebAuthenticationSession
  → User logs in, Safari redirects back to app
  → AuthenticationService.loginWithOIDCCallback(url)
    → client.loginWithOidcCallback(...)        // Rust completes OIDC

User chooses username/password:
  → AuthenticationService.login(username:password:)
    → client.login(username:password:...)      // Rust POST /login
```

After login, a `RestorationToken` is saved to the **iOS Keychain** (like Flutter's `flutter_secure_storage`).

### Session Restoration (App Restart)

**File:** `ElementX/Sources/Services/UserSession/UserSessionStore.swift`

```swift
func restoreUserSession() async -> Result<UserSessionProtocol, UserSessionStoreError> {
    // 1. Read token from Keychain
    let credentials = keychainController.restorationTokens().first
    
    // 2. Rebuild the SDK client from stored data (no login required)
    let client = try await ClientBuilder
        .baseBuilder(...)
        .sqliteStore(...)
        .build()
    
    // 3. Wrap in ClientProxy
    let clientProxy = try await ClientProxy(client: client, ...)
    return .success(UserSession(clientProxy: clientProxy, ...))
}
```

The `RestorationToken` contains: access token, homeserver URL, device ID, session directories. The user is never asked to log in again.

## 16. End-to-End Encryption & Recovery Key

### What it is

All Matrix messages are encrypted with per-room **Megolm** keys. Those keys are backed up to the server in an encrypted **key backup**, protected by your **Recovery Key** — a long random string the user saves somewhere safe.

If you lose all devices, entering the recovery key downloads and decrypts your backed-up keys, restoring access to message history.

### Recovery state machine

```
.unknown    → app just started, hasn't checked yet
.disabled   → recovery has never been set up → shows "Set up Recovery" yellow banner
.enabled    → recovery key exists and backup is current → green, no banner
.incomplete → key exists but this device doesn't have it → shows "Confirm your key" banner
.settingUp  → generation in progress
```

**File:** `ElementX/Sources/Services/SecureBackup/SecureBackupController.swift`

### Generating a recovery key (first time)

```swift
func generateRecoveryKey() async -> Result<String, SecureBackupControllerError> {
    let key = try await encryption.enableRecovery(
        waitForBackupsToUpload: false,
        passphrase: nil,
        progressListener: SDKListener { state in
            // .creatingBackup, .creatingRecoveryKey, .backingUp, .done
        }
    )
    return .success(key)
}
```

What the Rust SDK does internally:
1. Generates a 256-bit random recovery key
2. Creates a new key backup (`POST /room_keys/version`)
3. Sets up SSSS (Secure Secret Storage) on your Matrix account
4. Uploads all existing room keys (`PUT /room_keys/keys`)
5. Returns the key string to Swift

### Confirming an existing key

```swift
func confirmRecoveryKey(_ key: String) async -> Result<Void, SecureBackupControllerError> {
    try await encryption.recover(recoveryKey: key)
    return .success(())
}
```

Rust SDK downloads the backup, decrypts with the provided key, imports room keys locally.

### How the banner appears on the home screen

```
SecureBackupController (Rust listener)
  → recoveryStateSubject.send(.disabled)          ← Combine subject
    → UserSession.sessionSecurityStatePublisher   ← combined with verification state
      → HomeScreenViewModel subscriber
        → state.securityBannerMode = .show(.setUpRecovery)   ← ViewState
          → HomeScreen renders the yellow banner
```
